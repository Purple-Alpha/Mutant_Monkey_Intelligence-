## 1. Executive Risk Summary

The patched `MMI Scratch Archive Content Secret Scan Specification` represents an outstanding, defense-in-depth specification with mature, deterministic control gates. It enforces extensive archive safety, unicode handling, and least-privilege constraints. However, under adversarial scrutiny, several critical architectural and regex-level flaws persist that could allow a determined threat actor or standard build compiler to bypass content scans, or trigger Denial of Service (DoS) states on the execution host:

- **ReDoS Vulnerability in Wildcard Configurations:** Multiple regexes utilize loose alternations and unanchored wildcards that invite catastrophic backtracking when evaluating long source code strings.
- **HMAC Salt Entropy Leakage:** The specification lacks a secure lifecycle for the HMAC secret salt, which risks exposing the true identities of redacted keys via dictionary attacks.
- **Unicode Zero-Width Bypass Vectors:** The normalizer's Unicode translation layer is vulnerable to character-insertion bypasses where compiler engines parse keys that the regex engine fails to match.
- **Archive Extraction & Symlink Cycles:** There is a logical gap in defining link-traversal bounds during the extraction phase, leaving the host vulnerable to file-system escape.

---

## 2. Critical Blindspots & Flaws

### 1. Static Salt Lifecycle & HMAC Dictionary Reversibility
- **Location/Context:** Section 29 (Redaction HMAC Policy).
- **The Exploit/Failure Scenario:** If the HMAC salt is static, written to disk, or hardcoded in the scan tool, any developer or adversary with access to the redacted reports can generate offline lookup tables of common token formats (such as 40-character OpenAI keys or 32-character hex keys) and run high-speed dictionary attacks to fully reverse the redacted `hmac_prefix_12` fingerprints, revealing the active production secrets.
- **The Precise Remediation:** Replace the first paragraph of Section 29 with:
  > Secret fingerprinting must use HMAC-SHA256 with an ephemeral, runtime-only secret salt. The salt MUST be generated using a cryptographically secure pseudo-random number generator (CSPRNG) at scanner startup, held strictly in-memory, and destroyed immediately upon execution completion. All public artifacts must use this run-unique HMAC to prevent offline cross-report key correlation and dictionary lookup attacks.

### 2. Catastrophic ReDoS in Private Key Wildcard Pattern
- **Location/Context:** Section 20 (Private Key Block Pattern).
- **The Exploit/Failure Scenario:** The pattern `BEGIN .* PRIVATE KEY` uses an unbounded wildcard `.*`. If evaluated against a massive log file, non-ascii binary data, or a carefully crafted C++ source file containing 50,000 characters of repeating hyphens on a single line, the regex engine will experience catastrophic backtracking, pinning the CPU at 100% and triggering a thread hang (Denial of Service).
- **The Precise Remediation:** Replace the "Private key block" pattern in Section 20 with:
  > `BEGIN (RSA|EC|DSA|OPENSSH)? PRIVATE KEY`

### 3. Unicode Zero-Width character Bypass (Anti-Regex Obfuscation)
- **Location/Context:** Section 28 (Unicode and Control Character Handling).
- **The Exploit/Failure Scenario:** An adversary can embed a Zero-Width Space (`\u200B`), a Zero-Width Non-Joiner (`\u200C`), or a soft hyphen in the middle of a hardcoded API key (e.g., `sk-ant\u200B-...`). Standard regex patterns will fail to match this key. However, when the driver compilation chain or Go build tool processes the file, the compiler's pre-processor may silently strip control characters, resulting in a fully functional, compiled, but completely unscanned credential bypass.
- **The Precise Remediation:** Replace the text of Section 28 with:
  > **Unicode Normalization and Sanitization Pipeline:**
  > Prior to any regex execution, the scanner's input normalizer MUST:
  > 1. Detect UTF-8, UTF-16LE, and UTF-16BE encoding formats.
  > 2. Normalize text to Unicode Normalization Form C (NFC).
  > 3. Strips all zero-width characters (`\u200B`, `\u200C`, `\u200D`, `\uFEFF`) and control characters (`\u0000` to `\u0008`, `\u000B`, `\u000C`, `\u000E` to `\u001F`) from the textual copy *before* rules are evaluated.
  > 4. If any zero-width space or control character is stripped within 10 characters of an alphanumeric string, record: `UNICODE_CREDENTIAL_CONTEXT_REVIEW` with blocker status.

### 4. Recursive Extraction and Symlink Traversal Loophole
- **Location/Context:** Section 24 and Section 25 (Archive Safety / Safe Extraction).
- **The Exploit/Failure Scenario:** The scratch archive contains absolute Windows paths and may support symlinks. If a malicious or corrupted archive defines a directory symlink that references `/etc` or `/mnt/c/Windows/System32`, and the scanner extracts entries using standard library routines, it will write files outside the temporary isolated scan root, causing host file system overwrite or metadata leakage.
- **The Precise Remediation:** Replace the "Reject or block" list in Section 24 with:
  > **Absolute Disallowance List (Hard Fail on Ingestion):**
  > The scanner must immediately abort execution with `ARCHIVE_SAFETY_BLOCKER` status if any of the following are detected:
  > 1. Any path containing `..` or leading slashes.
  > 2. Any symlink or hardlink whose resolved target escapes the designated ephemeral isolated scan root.
  > 3. Any device files, named pipes, or socket files.
  > 4. Any compression ratio exceeding 100:1.
  > 5. Any archive containing Unicode-normalized path collisions (representing directory spoofing attempts).
